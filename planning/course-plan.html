2. Ask Jev your first questions

3. Choose the right question type

4:30. API request editor. Then run one combined request.

  • Choice: Which team? Select one known option.
  • Noul: Does the customer request a person? Estimate yes-probability.
  • Score: How urgent? Define clear ordered levels.
  • Show the request and response for each type.
  • Send independent questions together using the same state.
  • Practise choosing, checking, or scoring a new scenario.
Examples and teaching boundaries
  • Use a prepared Python request with the official SDK. Keep the HTTP body visible beside the response in the editor.
  • Use “I was charged twice. Fix this today and connect me to a real person.”
  • Choice reuses the four teams from video two.
  • Noul asks whether the customer explicitly requests a human. A generic request for help does not count.
  • Urgency levels: no timing pressure; attention within days; needed today; immediate outage or deadline within hours.
  • 0:00-0:25: introduce the three answer shapes.
  • 0:25-1:15: recap Choice. 1:15-2:10: run Noul.
  • 2:10-3:15: define and run Score. 3:15-3:55: combine the questions.
  • 3:55-4:30: let learners select the type for a new example.
  • Noul near 0.5 means uncertainty about yes or no. A middle Score represents a position on the rubric.
  • Choice and Score include confidence. Noul has no separate confidence field.
  • Questions in one request cannot see one another's answers. Code combines them afterward.
  • Several labels may apply? Use independent Nouls rather than forcing one Choice.

5. Handle uncertainty in your decisions

4:30. Same app. Codex adds the review policy.

  • Try the resume with conflicting production-deployment claims.
  • Inspect competing answers and confidence.
  • Flag low confidence, conflicting claims, and missing evidence for review.
  • Use a yes/no uncertainty band for Noul.
  • Change a threshold without calling Jev again.
  • Compare evidence labels with review flags. Count both outcomes.
Codex prompt and demonstration 
Add a pure policy function over saved Jev answers. Route low-confidence Choice or Score answers, Other, missing evidence, and API failures to review. For the production-delivery Noul, make the no/uncertain/yes boundaries configurable. Keep not-stated evidence distinct from proof that a candidate lacks a skill. Changing thresholds must not make another API request. Keep exact business rules in code. Show why each review decision occurred.
  • 0:00-0:40: inspect the conflicting resume evidence.
  • 0:40-1:40: compare the distribution, top probability, and returned confidence.
  • 1:40-2:40: inspect the new policy and show a manual-review result.
  • 2:40-3:45: move the threshold over the saved response. Show the unchanged API-call count.
  • 3:45-4:30: compare clear and unclear cases. Explain the quality versus review-volume tradeoff.
  • If the live example returns high confidence, show that result honestly. Use a saved real ambiguous run, or an explicitly labeled illustration, to explain a split distribution.
  • Example Noul boundaries of 0.2 and 0.8 are teaching defaults to evaluate. They are not universal recommendations.
  • Confidence summarizes the distribution. It does not mean “this complete workflow is correct with that probability.”
  • High confidence can still be wrong. Missing evidence needs review even when the model sounds certain.
  • Default to a person for review. A stronger LLM fallback adds another call and must be included in total cost and time.

6. Test your Jev decision workflow

4:30. API examples and a saved evaluation report.

  • For each use case: define evidence, answer, action, fallback, and test.
  • ATS matching: classify evidence for a job requirement with Choice.
  • Agent request: check for an external action with Noul.
  • Content shortlist: score audience fit with Score.
  • Run clear, ambiguous, and missing-context examples.
  • Check routing errors, missed handoffs, time, and cost.
  • Improve on practice cases. Check fresh cases before finishing.
The reusable decision framework and three examples

First ask: “What am I repeatedly reading just to choose, check, or score something?”

Use [evidence] to [choose, check, or score].
Then code [takes an action].
If unclear, [use a fallback].
Test against [expected outcomes].

If an exact rule or lookup solves the task, use code. If the output must be new prose or a long plan, use an LLM. A larger workflow can contain all three.

ATS matching: Choice

  • Evidence: job requirement and numbered resume statements.
  • Answer: direct, related, not stated, or unclear.
  • Action: display the evidence and flag cases needing recruiter review.
  • Fallback: request details or send it for review.
  • Test: compare evidence labels and review flags with human labels.

Agent requests: Noul

  • Evidence: user request and the permitted-action policy.
  • Answer: does the request explicitly ask to send, delete, book, or update something?
  • Action: flag the request for the approval workflow.
  • Fallback: clarify ambiguous scope. Keep access permissions in code.
  • Test: “draft an email” versus “send that email,” plus an ambiguous request.

Content shortlist: Score

  • Evidence: video idea and an explicit audience definition.
  • Answer: unrelated, general interest, practical relevance, or reusable high-priority workflow.
  • Action: shortlist ideas above the chosen fit threshold.
  • Fallback: request a clearer idea or let the editor review it.
  • Test: strong, weak, and borderline ideas against editor judgments.
  • The score measures the rubric. It does not predict views or virality.

Codex evaluation prompt:

Add labeled practice cases and a separate held-out set for the three examples. Include ordinary inputs, ambiguous inputs, missing evidence, no-match inputs, and a simulated API failure. Keep the held-out set out of prompt tuning. Report per-case answers, policy outcomes, errors, review rate, missed reviews, median latency, and token-based estimated API cost. Save raw responses and model IDs. Use the same inputs and label definitions for an optional LLM comparison.
  • 0:00-0:40: introduce the five-part framework.
  • 0:40-3:10: spend 50 seconds on each worked example.
  • 3:10-4:05: inspect the prepared evaluation report and one failure.
  • 4:05-4:30: change one question on practice data. Finish with a fresh case.
  • Suggested teaching set: 20 practice cases and 10 held-out cases, balanced across the three examples.
  • Use expected action or acceptable label ranges when several answers are defensible.
  • A correct handoff is useful behavior. Report review rate alongside routing accuracy.
  • Include fallback costs when comparing complete workflows. A small course test set does not establish production readiness.
